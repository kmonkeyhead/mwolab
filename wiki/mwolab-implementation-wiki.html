MwoLab 구현 위키

기준일 2026-08-27 · 현재 저장소 구현 기준

이 문서는 MwoLab이 무엇을 만들려는 도구인지, 각 기능을 왜 그 방식으로 설계했는지, 실제 구현과 계산은 어떤 기준을 따르는지를 함께 설명하는 내부 기획·구현 가이드다.

문서 운용 원칙
구현 전에는 관련 위키 내역을 참고한다. 단, 현재 코드와 새로 추출한 게임 데이터가 항상 우선하며 위키와 충돌하면 실제 구현을 확인한 뒤 판단한다. 사용자가 기능 구현이나 코드 수정을 명령하면 작업 완료 후 재사용 가능한 규칙이 추가·변경·명확화되었는지 판단하고, 필요하면 별도의 “위키 갱신” 요청을 기다리지 않고 같은 작업에서 즉시 위키도 갱신한다. 모든 작업 뒤 기계적으로 갱신하는 것은 아니다. 이 파일은 앱과 분리된 내부 문서이며 사용자가 요청하지 않는 한 앱에 링크를 추가하지 않는다.

제작 의도와 방향성

MwoLab의 목표는 MWO의 방대한 원본 데이터를 단순히 나열하는 것이 아니라, 사용자가 멕을 찾고 빌드를 만들고 여러 선택지를 비교한 뒤 실제 운용 특성을 예상하는 전 과정을 한 도구 안에서 이어 주는 것이다. 게임 클라이언트를 켜지 않아도 “이 장비가 장착되는가”, “쿼크와 스킬을 적용하면 무엇이 얼마나 바뀌는가”, “거리와 발열을 고려하면 어떤 구성이 유리한가”를 같은 기준으로 판단할 수 있어야 한다.

핵심 기획 방향
  • 판단 가능한 정보: 숫자만 보여 주지 않고 기본값, 보정 근거, 최종값과 비교 맥락을 함께 제공한다.
  • 게임 데이터 충실성: 이름이나 경험칙으로 값을 추정하지 않고, 설치된 게임의 원본 데이터와 현재 코드를 계산의 최종 근거로 삼는다.
  • 화면 간 일관성: 같은 멕·무기·쿼크는 어느 탭에서 보더라도 같은 공식과 단위로 계산되어야 한다.
  • 실전 지향성: 정적 스펙뿐 아니라 거리별 피해, 지속 화력, 발열, 탄약, 재밍처럼 실제 빌드 운용에 영향을 주는 요소를 함께 보여 준다.
  • 빠른 탐색: 전체 데이터를 반복 계산하지 않고 캐시와 선택 단위 갱신을 사용해 필터·비교·피팅 흐름을 끊지 않는다.
  • 검증 가능한 구현: 계산식은 코드와 테스트에서 재현할 수 있어야 하며, 위키에는 공식과 경계 조건을 함께 기록한다.

기획 경계: MwoLab은 정적 브라우저 도구를 유지하며 자체 서버 런타임은 운영하지 않는다. 핵심 멕랩은 로컬 저장과 MWO 코드 호환을 우선하고, 공개 핏팅에만 Google Authentication과 Cloud Firestore 관리형 서비스를 사용한다. 게임 데이터에서 확인할 수 없는 값은 임의로 보완하지 않는다. 시뮬레이션은 빌드의 상대적 성능과 운용 경향을 비교하기 위한 계산 도구이며 게임 클라이언트 전체 물리·네트워크 환경을 재현하는 것을 목표로 하지 않는다.

현재 상태

MwoLab은 MechWarrior Online의 로컬 게임 데이터를 정적 JSON으로 변환해 사용하는 브라우저 기반 멕 피팅·정보·비교 도구다. 설치와 운영 부담을 낮추고 데이터 출처를 투명하게 유지하기 위해 별도 프레임워크나 서버 API 없이 public 폴더만으로 배포할 수 있게 설계했다.

공통 규칙

public/styles.css의 문서 루트·스크롤 컨테이너와 public/mobile/mobile.css의 스크롤 영역은 scrollbar-gutter: stable을 사용한다. 세로 스크롤 뷰는 overflow-y: scroll을 함께 지정해 내용이 짧을 때도 스크롤바 영역을 차지한다. 공용 스크롤바 CSS는 트랙·코너를 투명하게 하고 버튼을 숨기며, 스크롤 가능한 경우의 손잡이만 그 공간에 표시한다. 왼쪽 mech-summary-panel도 포함하며 표시 원칙은 프로젝트 규약 에이전트.md를 따른다.

  • 근거 우선순위: 사용자의 최신 요구 → 현재 코드의 실제 동작 → 새로 추출한 게임 데이터 → 이 위키의 기존 설명 순서로 판단한다. 위키는 구현 가이드이지만 코드나 게임 데이터를 덮어쓰는 원본은 아니다.
  • 동일 계산: 정보보기·비교하기·통계·멕랩에서 같은 수치를 보여 줄 때는 같은 원본 데이터, 정규화 함수, 쿼크 계산을 재사용한다.
  • 데이터 우선: 멕, 장비, 로드아웃, 옵니포드 수치는 이름별 하드코딩보다 public/data의 속성과 재사용 인덱스에서 가져온다.
  • 선택 상태: 주 탭은 state.activeMainTab을 기준으로 한다. 멕랩 피팅은 state.mechlabTabs의 탭별 멕 ID와 빌드 객체가 소유하고 state.activeMechlabTabId가 마지막으로 활성화한 채워진 피팅을 정한다. state.mechlabPendingTabIndex가 현재 탭 개수와 같으면 마지막 + 빈 슬롯이 논리적 포커스다. state.selectedMech와 state.currentBuild는 활성 주 화면 또는 마지막 활성 피팅 탭의 작업용 참조다. 정보보기 선택은 state.selectedMechIdsByTab.info, 비교 대상은 state.compareMechIds, 통계 선택은 state.selectedStatsMechId가 담당한다. 주 화면이나 피팅 탭 전환만으로 다른 피팅을 덮어쓰지 않는다.
  • 탭 수명주기: 숨겨진 주 탭은 불필요하게 미리 렌더링하지 않는다. 탭 전환 시 그 탭에 필요한 렌더 함수만 호출하고 URL의 멕 및 tab 상태와 동기화한다.
  • 표현 일관성: 하드포인트 태그, 멕 슬롯, 쿼크 색상, 숫자 단위와 빈 값 표시는 화면마다 별도로 복제하지 말고 공용 렌더링 규칙을 따른다.
  • 사이트 제목: 공개 페이지의 HTML 문서 제목은 검색어와 사이트 성격을 함께 나타내는 mwolab - MechWarrior Online MechLab을 사용한다.
  • 성능: 추출 데이터는 게임 갱신 전까지 정적이라고 보고 반복 파생값을 브라우저 메모리에 캐시한다. 선택만 바뀌는 경우 전체 목록을 재계산하거나 재생성하지 않는다.
  • 검증: 수정한 범위의 구문, 데이터 구조, 계산 회귀, git diff --check를 확인한다. 사용자가 요청하지 않으면 로컬 미리보기 서버를 시작하거나 검사하지 않는다.

구조와 데이터 흐름

정적 배포의 단순함을 유지하면서도 모든 화면이 같은 계산 결과를 공유하도록 HTML이 화면 골격을 제공하고, 하나의 전역 상태 객체를 중심으로 app.js가 데이터 로딩·계산·렌더링·이벤트를 처리한다. 계산 규칙이 화면마다 갈라지지 않도록 MWO 로드아웃 문자열 변환은 mwo-codec.js, 공용 쿼크 계산은 quirk-calculations.js에 분리한다.

MWO 설치 파일 → extract_mwo_data.py → public/data/*.json → init() → state → 계산 함수 → 화면 렌더링
  1. init()이 index.json과 멕·장비·영문 현지화·로드아웃·옵니포드·스킬 JSON을 읽는다.
  2. 읽은 데이터는 state에 저장되고, 검색·쿼크·하드포인트용 파생 인덱스는 브라우저 메모리 캐시에 만든다.
  3. 멕 선택 시 기본 로드아웃 또는 저장된 빌드를 currentBuild로 구성한다.
  4. calculateBuild()가 중량, 슬롯, 아머, 장비, 탄약, 엔진, 발열과 경고를 계산한다.
  5. 각 탭의 렌더 함수가 동일한 원본 데이터와 계산 기준을 사용해 화면을 갱신한다. 보이지 않는 주 탭은 미리 렌더링하지 않는다.

추출된 숫자는 게임 데이터 갱신 전까지 사실상 정적이다. 반복 계산이 큰 값은 JSON에 다시 저장하지 않고 브라우저 메모리에서 캐시한다.

FirePower는 Cooldown, Range, HeatGen, Velocity, 나머지 노드의 다섯 독립 토글로 세분화하고 Operations는 CoolRun+HeatContainment를 묶은 히트싱크 강화와 나머지 노드의 두 토글로 세분화한다. Survival, Mobility, Jump Jets, Sensors, Auxiliary는 카테고리 전체를 하나의 토글로 유지한다. 각 버튼에는 그룹 이름과 포함 노드 수만 표시하고 효과 설명은 표시하지 않는다. 활성 항목은 그 그룹에서 현재 멕이 사용할 수 있는 모든 노드를 찍은 것으로 계산하고, 모두 적용은 모든 세부 그룹을 한꺼번에 켜거나 끈다. 스킬이 하나 이상 활성화되면 왼쪽 피팅 정보 패널의 기존 QUIRKS 구역보다 앞에 SKILL + QUIRKS 구역을 표시한다. 이 구역은 스킬과 차체·옵니포드·세트 쿼크를 이름별로 합산한 최종값만 한 목록으로 보여 주며 CT, SO6, SO8, 출처 툴팁처럼 옵니포드 출처를 구분하는 정보는 넣지 않는다. 기존 QUIRKS 이하 구역은 스킬을 섞지 않은 원래 쿼크와 출처 구분을 그대로 보여 준다. 노드 효과는 멕랩 피팅 요약, 장비 툴팁과 사격 시뮬레이션 계산에만 적용하고 정보보기·비교·통계의 정적 멕 수치에는 섞지 않는다. Operations의 HeatContainment maxheat_multiplier는 기본 멕 열용량 30과 엔진 내장·추가 히트싱크 합계가 10개를 넘은 뒤의 외부 히트싱크 HEAT CAPACITY에만 곱한다. 엔진 구간인 최초 10개의 ENGINE CAPACITY에는 적용하지 않는다. 이 규칙은 멕랩 HEAT CAPACITY와 사격 시뮬레이션 MAX HEAT·과열 기준에 동일하게 적용하며, 히트싱크 장비 툴팁에서는 HEAT CAPACITY에만 기본값·스킬/쿼크 기여·최종값을 표시하고 ENGINE CAPACITY는 원본 값만 표시한다. 진영·체급·톤수·개별 멕으로 중첩된 값은 가장 구체적인 일치 값을 사용하고, 점프젯·ECM·미사일 하드포인트 같은 Require 조건과 360도 몸통 회전 제외 같은 멕 속성 조건을 만족하지 않는 노드는 제외한다. JSON의 톤수 범위 이름은 문자열이므로 실제 멕 톤수와 비교하기 전에 유효한 숫자로 명시 변환한다. Survival의 전체 아머·스트럭처 배율은 기존 부위별 쿼크가 적용된 값에 곱해 멕랩 최대 내구도와 컴포넌트 표시를 계산하고, 스킬이 적용된 각 부위의 최종 아머·스트럭처 값은 소수점을 버린 뒤 합산한다. 컴포넌트의 현재 아머는 한 부위의 실제 전면·후면 배분값과 양쪽 쿼크를 먼저 합산한 뒤 스킬 배율을 한 번 적용한다. 이때 스킬로 생긴 증가분은 전면 표시에 더하고 후면은 배분값과 후면 쿼크만 표시한다. 따라서 전·후면 아머를 모두 제거했을 때의 전면 최소 표시는 기본 최대치에서 생긴 스킬 증가분을 포함하지 않고, 해당 부위 쿼크에 적용된 스킬 증가분만 포함한다. 왼쪽 피팅 정보의 현재 아머도 이 부위별 최종값을 합산하고, 최대 아머는 부위별 최종 최대값을 합산한다. 중량은 스킬·쿼크로 늘어난 내구도가 아니라 실제 배분한 원본 아머만 사용한다. 두 효과도 SKILL + QUIRKS 합산 목록에 포함한다. 선택 상태와 파생 효과는 브라우저 메모리에만 유지하며 빌드 JSON이나 생성 데이터에 역으로 기록하지 않는다.
  • 추천 스킬 적용: 스킬 선택 UI에서 모두 적용과 추천 스킬 적용을 각각 한 행 전체를 차지하는 강조 버튼으로 표시하고 추천 버튼은 모두 적용 바로 아래에 배치한다. 추천 버튼을 누르면 기존 선택을 교체하고 FirePower의 Cooldown·Range·HeatGen·Velocity, Survival 전체, Operations의 CoolRun+HeatContainment 히트싱크 강화 그룹만 활성화한다.
  • 탄약 쿼크 표시 간소화: 개인설정에서 켜고 끄며 기본값은 OFF다. ON이면 왼쪽 피팅 정보 패널의 SKILL + QUIRKS와 기존 쿼크 구역에서 개별 탄약 쿼크를 모두 숨기고, 탄약 쿼크가 하나라도 있을 때 탄약 쿼크 적용중 한 줄로 대체한다. 이 설정은 왼쪽 표시만 바꾸며 쿼크 계산, 장비 툴팁, 정보보기·비교·통계 등 다른 화면에는 적용하지 않는다.
  • 시뮬레이션: 현재 빌드의 무기만 사용하며 실제 피팅 쿼크, 탄약, 잼, 고스트 힛과 발열 조건을 반영한다.

멕 요약, 하드포인트 배지, 슬롯 배지, 쿼크 값, 무기별 쿼크 검색 인덱스, 고정 옵니 엔진, 무장 정보 HTML 등은 Map 또는 재사용 인덱스로 캐시한다. 통계는 statsEntriesCache에 조건별 순위 결과를 최대 64개까지 보관하고, 동일 조건에서는 data-stats-rows-key로 현재 DOM을 재사용한다. 선택만 바뀔 때 통계 전체 목록을 다시 계산하거나 재생성하지 않는다.

  • 멕랩 요약은 최종 빌드 계산의 결과이며 화면에 보이는 슬롯을 다시 세어 별도 합계를 만들지 않는다.
  • 고정 장비와 이동식 장비, 차체와 옵니포드 출처를 잃지 않아야 하드포인트 점유와 중복 내부 장비를 정확히 계산할 수 있다.

피팅·슬롯 규칙

제작 의도: 장비 카드를 화면에 놓는 행위와 게임에서 장착 가능한 빌드를 만드는 행위를 동일하게 취급한다. 드래그, 클릭, 코드 불러오기 등 진입 경로가 달라도 같은 슬롯·하드포인트·중량·수량 제한을 통과해야 한다.

컴포넌트 순서

Head → Left Arm → Left Torso → Center Torso → Right Torso → Right Arm → Left Leg → Right Leg 순서를 유지한다. 후방 토르소 아머는 독립 장비 카드가 아니라 아머 계산에만 포함한다.

슬롯과 하드포인트

  • 사용 슬롯 = 컴포넌트 내부 고정 항목 수 + 장착 아이템의 stats.slots 합계다.
  • 슬롯 한도는 컴포넌트의 slots를 사용한다.
  • 무기 장착 수용량은 하드포인트의 weapon_slots를 사용한다. 원본 MDF의 Slots 속성은 무기 개수가 아니다.
  • weapon_slots 매핑이 실제로 없는 경우에만 1을 폴백으로 사용한다.
  • 옵니멕은 현재 장착한 옵니포드 하드포인트를 최우선으로 사용한다.
  • 옵니멕의 차체 고정 무기는 옵니포드 하드포인트를 점유하지 않지만, 옵니포드 자체의 고정 무기는 해당 하드포인트를 점유한다. 계산과 장착 검증에서 고정 장비의 출처를 함께 보존한다.
  • 차체와 옵니포드가 제공하는 내부 고정 장비는 같은 ID라도 각각의 실제 장착분이므로 중복 제거하지 않는다.
  • 옵니포드 귀속 장비, SHOULDER·HIP 같은 내부 고정 슬롯, XL 엔진 측면처럼 사용자가 움직일 수 없는 슬롯은 고정 옵니 엔진과 같은 그라데이션 없는 단색 진회색 블록으로 표시한다. 이동식 슬롯보다 어두운 배경, #7d878a의 저채도 글자, 굵은 좌측 고정 레일과 내부 테두리를 사용해 빈 슬롯 및 이동식 장비와 구분한다. 멕랩 장비 패널의 장비 목록 행 최소 높이는 1.5rem으로 유지한다.
  • 장착 후 위치가 확정되어 움직일 수 없는 아머·스트럭처 업그레이드 점유 슬롯도 좌측 고정 레일, 내부 테두리, 굵은 글자 규칙을 따른다. 좌측 레일과 글자는 일반 고정 슬롯의 회색을 사용하고, 아머와 스트럭처의 점유 배경·테두리도 같은 차콜 회색 계열로 통일한다. 아직 점유되지 않은 업그레이드 슬롯에는 적용하지 않는다.
  • 스텔스 아머는 좌우 팔, 좌우 몸통, 좌우 다리에 각각 2칸씩 총 12칸을 고정 점유한다. 이 슬롯은 다른 부위로 이동하거나 장비 장착 시 밀려나지 않으며, 어느 부위든 필요한 2칸이 부족하면 해당 부위 슬롯 초과와 아머 업그레이드 슬롯 부족을 경고한다. 머리와 중앙 몸통에는 스텔스 아머 슬롯을 배치하지 않는다.
  • 하드포인트 ID는 선행 0을 제거해 정규화한 뒤 비교한다.

장비 필터와 장착

  • 에너지·미사일·발리스틱·AMS는 해당 유효 하드포인트가 있을 때만 목록에 표시한다.
  • ECM, 점프젯, MASC는 멕 능력과 톤수 조건을 모두 만족해야 한다.
  • C.A.S.E., Active Probe, Target Computer처럼 원본 데이터에 장착 수량이나 허용 부위가 지정된 장비는 그 제한을 검증한다.
  • 드래그 앤 드롭과 클릭 자동 장착은 동일한 dropValidation 규칙을 거친다.
  • 장착 후 중량 초과, 슬롯 초과, 하드포인트 부재, 엔진 범위, 장비 수량 제한을 계산해 경고한다.

업그레이드와 MWO 코드

  • 아머, 스트럭처, 히트싱크, 아르테미스 업그레이드를 빌드 상태로 관리한다.
  • 아르테미스 적용/해제 시 표시 이름만 바꾸지 않고 무기와 탄약 ID를 양방향으로 교체한다.
  • 표준 → 아르테미스 → 표준 왕복 후 원래 ID가 복원되어야 한다.
  • alwaysHasArtemis 무기는 선택형 변환 대상이 아니다.
  • mwo-codec.js는 6비트 문자 형식의 직렬화만 담당하고, 실제 멕·장비 검증은 app.js에서 한다.

쿼크 규칙

제작 의도: 쿼크를 단순 문자열 목록이 아니라 실제 성능 변화로 연결하되, 사용자가 기본값과 보정 기여를 구분할 수 있게 한다. 일반·계열·무기 전용 쿼크의 중첩은 모든 화면에서 같아야 하며, 이로운 감소와 해로운 증가의 부호를 잃지 않는다.

쿼크 이름 정규화와 +수치 합산, multiplier/additive, 감소·증가·부호 보존, 유해 수치 판정 같은 공용 계산은 public/quirk-calculations.js에 둔다. app.js의 화면·피팅·시뮬레이션은 이 모듈을 공유하며 같은 공식을 다시 구현하지 않는다.

  • 쿼크 이름과 무기 검색 키는 대소문자를 구분하지 않도록 정규화한다.
  • 요약 값은 일반 쿼크 + 무기 계열 쿼크 + 가장 잘 맞는 무기 전용 쿼크를 합친다.
  • 쿨다운·발열·지속시간·산포처럼 감소가 이득인 multiplier는 음수로 저장되므로 이득 요약에는 Math.max(0, -value)를 사용한다. 단, 무기 듀레이션·스프래드 multiplier가 양수면 악영향이므로 무기 계산에서는 부호를 유지해 최종값을 증가시키며 0으로 버리지 않는다.
  • 사거리·탄속·열 방출·ROF처럼 증가가 이득인 multiplier는 Math.max(0, value)로 요약한다.
  • 무기 전용 쿼크는 통계 접미사를 제거한 이름을 장비의 이름·표시 이름·원본 표시 이름·별칭과 매칭한다.
  • 무기 계열은 개별 이름 하드코딩보다 장비 데이터의 hardpoint_type 또는 stats.type을 우선한다.

요약 카드

  • 쿨다운: MAX, ENERGY, MISSILE, BALLISTIC.
  • 발열: MAX, ENERGY, MISSILE, BALLISTIC, HEAT DISSIPATION.
  • 사거리·탄속: MAX, ENERGY, MISSILE, BALLISTIC.
  • 듀레이션/ROF: 레이저 듀레이션과 가장 높은 ROF를 5% / 3% rof 형태로 한 행에 표시한다.
  • 산포: 에너지 항목이 없지만 시각 정렬을 위해 빈 위치를 유지한다.
  • 내구도: 부위별이 아니라 MAX(아머+스트럭처), 아머, 스트럭처, 크리티컬 방지의 총합만 표시한다.
  • 특수: 현재 ECM, 점프젯, NARC 지속시간을 인식한다.

쿼크 서머리는 QUIRKS 목록 안이 아니라 독립 정보 카드다.

값 색상

기본값과 쿼크 기여도를 함께 표시하는 경우 최종값은 초록색, 쿼크 기여도는 노란색이다. 무기 듀레이션·스프래드에 적용된 multiplier 합계가 양수인 악영향이면 최종값과 쿼크 기여도를 모두 빨간색으로 표시하고, 기본값·괄호·연산자는 주변 통계의 기본 색을 유지한다. 원본 쿼크 목록에서도 해당 양수 쿼크 값은 빨간색으로 표시한다.

DPH와 MASC 툴팁

  • DPH는 발열 1점당 피해량(Damage Per Heat)이므로 damage / heat로 계산한다.
  • MASC 최종 기동성은 쿼크가 반영된 현재 값에 MASC 부스트를 곱한다: 쿼크 최종값 × (1 + MASC boost).
  • MASC 부스트가 0인 항목은 부스트 행과 최종값 행을 모두 표시하지 않는다.
  • 멕 핏팅의 점프젯 높이는 연소시간과 초기 추력 쿼크가 반영된 최종 수치로 계산하며, 요약에는 최종 결과만 표시한다.

에너지 레이저 예외

레이저 전용 쿼크는 레이저 무기에, 에너지 쿼크는 모든 에너지 무기에 적용한다. PPC도 에너지 쿼크의 영향을 받는다. 이름에서 구분되는 경우 표준 레이저 쿼크를 ER 또는 펄스 변형에 섞지 않는다.

무기 계산 규칙

제작 의도: 표시된 단일 damage 값만으로는 알 수 없는 펠릿·연속 발사·스플래시·사거리 감쇠·재밍·탄약 소비를 실제 선택 지표로 바꾼다. 계산은 장비 원본 속성에서 출발하며 특수 무기 이름을 예외로 늘어놓기보다 공통 데이터 구조를 우선한다.

피해와 연속 무기

  • 직격 피해는 기본적으로 damage × numFiring × 발사체 수다. 무기명·표시명·접미사의 숫자를 발사 수나 계산값으로 추론하지 않고 명시적인 추출 데이터 필드만 사용한다.
  • 로켓런처 쿨다운은 전체·미사일·무기별 스킬 및 쿼크 감소의 영향을 받지 않는다.
  • IS·Clan Streak SRM(SSRM) 2/4/6은 전탄 동시 발사 무기다. 원본에 volleydelay가 있어도 예상 쿨다운과 시뮬레이션 발사 시간에는 더하지 않는다.
  • 탄환형 펠릿 무기와 로켓런처는 명시적인 numPerShot을 발사체 수에 반영한다. 로켓런처 10/15/20은 추출값 1/2/3을 사용하며 무기명의 숫자는 사용하지 않는다.
  • 스플래시 총피해는 직격 + 양옆 부위의 스플래시를 합산한다.
  • 머신건·로터리 AC는 직격 피해 × ROF를 초당 피해로 표시하고 ROF 쿼크를 반영한다.
  • 빔레이저·화염방사기의 원본 피해는 초당값이므로 ROF를 다시 곱하지 않는다.
  • 머신건·로터리 AC·빔레이저·화염방사기는 연속형 무기이며 DAMAGE와 HEAT를 모두 초당값(/s)으로 표시한다. HPS와 시뮬레이션 발열은 원본 stats.heat를 사이클로 다시 나누지 않는다.
  • 레일건 커패시터 등 항상 적용되는 무기 모듈 보너스는 동일 진영의 장비 데이터에서 찾아 피해와 발열에 합산한다.

사거리와 특수 통계

  • 툴팁 사거리 순서는 MIN RANGE, OPTIMAL RANGE, MAX RANGE, VELOCITY다. 특수 통계 그룹은 원본 stats.spread를 SPREAD로 표시한다. stats.spreadLOS가 있으면 일반 퍼짐 그룹과 분리된 다음 특수 그룹에 같은 퍼짐 효과를 적용한 SPREAD DIRECT를 표시한다. 이 LOS 무기 중 stats.artemisAmmoType이 있는 LRM은 stats.speed × 1.4에 기존 탄속 효과를 적용한 VELOCITY DIRECT를 같은 그룹의 다음 행에 표시한다.
  • 사거리 쿼크는 MIN RANGE를 늘리지 않는다.
  • ATM은 60~349m, 350~649m, 650~1100m의 피해 구간을 사용하며 사거리 쿼크는 구간 상한과 최대 사거리에 반영한다.
  • 산포, 크리티컬 확률·피해, 대상 발열, 차지 시간은 데이터가 있을 때 별도 통계로 표시한다.
  • Ultra AC는 잼 지속시간과 잼 확률을 표시하며 관련 쿼크를 반영한다. 기대 DPM은 툴팁에 표시하지 않는다.
  • effectiveWeaponFiringProfile은 실효 numFiring, 실효 numPerShot, missile volleysize, 실효 volleydelay를 하나의 breakdown으로 만든다. 누락된 발사당 수량과 volley size는 1이다. 순차 SHOTS는 이벤트당 발사체 X 완전한 이벤트 수 + 나머지, 이벤트가 하나이거나 간격이 0인 전탄 동시발사는 전체 발사체 수만 표시한다. 같은 event count와 volley size를 예상 쿨다운과 시뮬레이션이 소비하며, 일반 단발 무기의 SHOTS 행은 숨긴다.
  • 개인설정의 장비 툴팁 적용 효과 표시가 ON이면 collectEquipmentQuirkEffects가 현재 피팅의 배리언트·옵니포드·세트·선택 스킬 중 해당 아이템에 기여하는 항목을 이름별로 합산해 값만 표시하며 이들의 출처는 표시하지 않는다. 무기는 기존 계산 수집기를 재사용하고, 비무기는 탄약 용량·실제 히트싱크·엔진·점프젯·MASC 툴팁 수치에 연결된 효과를 수집한다. ECM 장비는 ecmtargetrangereduction_multiplier와 stealtharmorcooldown_multiplier를 수신 효과로 수집한다. 탄약 용량은 일치하는 양수·음수 쿼크를 부호 그대로 합산한 뒤 톤수를 곱하고 한 번 내림하며, 표시값은 1톤은 원값, 0.5톤은 절반이다. 일반 센서·BAP와 공식상 무시되는 효과는 제외한다.
  • collectTargetComputerWeaponEffects는 장착 모듈별 weapon_stat_filters와 무기 원본 이름을 정확히 매칭해 기존 사거리·탄속·크리티컬 합계와 장비별 표시 기여를 함께 만든다. 적용 효과 렌더러는 쿼크·스킬 뒤에 장비 표시명을 출처 제목으로 둔 그룹을 배치한다. 장비명은 적용 효과와 같은 카테고리 제목색을 사용하고 효과명·수치에는 필터 태그가 아닌 대상 무기의 실제 하드포인트 계열에 맞는 quirk-tone-* 색을 적용한다. 크리티컬 확률은 critChanceIncrease CSV의 첫 번째 항목만 표시한다. Artemis 퍼짐과 항상 적용되는 Railgun Capacitor의 수량 합산 데미지·발열도 같은 최하단 장비 그룹으로 표시한다.
  • effectiveWeaponStats는 installedMechItems가 수집한 지원 모듈 occurrence와 무기 원본 이름에 정확히 일치하는 모든 weapon_stat_filters를 원본 순서로 순회한다. +는 기존 값 또는 누락 기본값 0에 더하고 *는 현재 값에 곱하며, 모듈·필터·스탯 인덱스와 연산 전후 값을 기여 내역으로 보존한다. 지원 필드 설정은 9031과 9032만 direct fold에 넣어 일반 Target Computer와 Railgun Capacitor의 기존 경로가 중복되지 않게 한다.
  • 9031의 HAG 필터는 spread +0.5, numPerShot +3, damage ×0.34, volleydelay ×0.7을 실제 계산에 적용하고 HAG20/30/40의 SHOTS는 3 X 4, 3 X 6, 3 X 8이 된다. Clan Gauss는 spread +0.25, numPerShot +4, damage ×0.25로 전탄 동시 SHOTS 4와 총 피해 15가 된다. C-AC10/20과 C-UAC5/10/20은 명시된 numFiring 감소와 damage 배율로 SHOTS 1·탄약 소비 1·표시 간격 없음이 되며 UAC Jam 공식은 그대로 유지한다. 크리티컬 원본 -1은 단계 없음 센티널이므로 장비 가산 후에도 X를 유지한다. PELLETS / SHOT, DAMAGE / PROJECTILE, PROJECTILES와 HAG·Clan Gauss의 SPREAD 연산은 계산에만 사용하며 자체 장비 툴팁과 무기 적용 효과에는 표시하지 않는다. HAG의 간격 배율만 대상 목록 없이 C.HAG INTERVAL ×0.7로 표시하며, 영향을 받은 무기 스탯의 최종 SHOT INTERVAL은 초록색 quirk-applied 스타일로 렌더링한다.
  • AMAROK의 고정 ID 9032 Modified Missile Loader는 C-LRM 5/10/15/20 일반·Artemis와 C-ATM 3/6/9/12 exact 필터의 numFiring, ammoPerShot, volleydelay, cooldown, MinReactivationTime을 공용 스냅샷에 적용한다. 피해·탄약·툴팁·DPS·빌드·시뮬레이션은 같은 최종값을 사용하고 원본 volleysize는 유지한다. 최종 SHOTS는 C-LRM20/15/10/5가 2 X 4, 2 X 3, 2 X 2, 2이고 C-ATM12/9/6/3이 1 X 8, 1 X 6, 1 X 4, 1 X 2다. 대소문자 변형을 정규화한 minReactivationTime은 결과에 보존하지만 timing에는 사용하지 않는다. 자체 툴팁과 무기 출처 그룹에는 기존 STREAM FIRE 설명만 표시한다.
  • AMS와 Laser AMS의 사거리 계산 및 적용 효과 목록은 공용 all_range_multiplier와 장비 이름·별칭에 일치하는 AMS 전용 사거리 쿼크를 함께 합산한다.

탄약

  • 탄약량은 장착 탄약 레코드의 stats.numShots를 사용하며 반톤과 1톤을 따로 존중한다.
  • 무장 정보 탄약 표는 일반 1톤 탄약만 사용하고 Artemis와 0.5톤은 제외한다. 톤수 열 없이 stats.health를 HP로, stats.internalDamage를 계산하지 않은 피폭 데미지로 표시한다.
  • 모든 탄약 표와 함께 정확히 연결된 무기 계열로 미사일·발리스틱 표를 나눈다. AMS 등 두 계열 밖의 탄약은 모든 탄약에만 남긴다.
  • 무장 정보의 정적 탄약 매칭은 추출 지침의 정확한 내부 이름 쌍에서 일반 무기 레코드의 ammoType과 _Artemis 레코드의 artemisAmmoType을 탄약 stats.type과 정규화해 연결한다. alwaysHasArtemis 무기는 원본 ammoType을 유지한다.
  • 정적 총 데미지는 같은 탄종의 최경량 무기를 기준으로 (numShots / 1회 소모량) × 스플래쉬 포함 기본 총데미지를 사용해 남은 탄의 피해까지 포함하며 거리 배율과 피팅 효과는 적용하지 않는다.
  • 정적 공유 탄약은 일반 1톤 탄종에 연결 무기가 둘 이상일 때 탄종별 독립 표를 만들고, 각 무기마다 floor(numShots / 1회 소모량)을 표시한다.
  • 활성 탄약 타입은 선택형 아르테미스 적용 시 artemisAmmoType, 그 외에는 ammoType이다.
  • 동일한 정규화 탄약 타입을 쓰는 무기들은 탄약 풀을 공유한다.
  • 동시 발사 가능 횟수는 매칭되는 탄약통의 합계를 묶인 무기들의 총 ammoPerShot으로 나눈다.
  • 탄약에도 적용되는 전용 무기 쿼크를 장비 필터와 비교 통계에 일관되게 반영한다.

고스트 힛

제작 의도: 높은 알파 화력이 실제로는 추가 발열 위험을 갖는다는 점을 빌드 단계에서 드러낸다. 외부 위키의 고정 표를 복제하지 않고 현재 게임 데이터의 그룹·임계치·페널티를 읽어 밸런스 변경에 다시 계산 가능하게 한다.

데이터와 계산 규칙

  • 외부 웹사이트의 표를 수치 원본으로 사용하지 않는다. 무기별 기본 발열, 페널티, 발생 시점, 그룹은 equipment.json의 heat, heatpenalty, minheatpenaltylevel, heatPenaltyID에서 읽는다.
  • 같은 heatPenaltyID의 무기를 동시에 발사해 무기별 발생 시점을 넘으면 고스트 힛 후보를 계산한다. 개별 그룹은 같은 무기끼리만 영향을 준다.
  • 같은 그룹 안에서도 AC/20과 Clan AC/20처럼 발생 시점이 다를 수 있고, AC/20과 Ultra AC/20처럼 추가 발열도 다를 수 있다.
  • 동시에 발생한 후보 중 가장 높은 추가 발열 하나만 기본 발열 합계에 더한다.
  • 고정 단계 상승 곡선은 코드에 두되, 무기별 수치와 그룹은 JSON에서 가져온다.
  • HSL 쿼크는 *_minheatpenaltylevel_additive 값을 사용한다. Ballistic·Energy·Missile 계열 HSL과 별칭으로 매칭되는 무기·패밀리 전용 HSL을 합산한다.
  • HSL은 고스트 힛 발생 여부를 검사하는 임계치만 뒤로 미룬다. 발생한 뒤에는 원래 임계치부터 현재 무기 수까지의 상승 단계를 모두 적용하므로 추가 발열 수치를 줄이지 않는다.
  • 예를 들어 임계치가 2인 AC/20은 HSL +1에서 2문 동시 발사로 발생하지 않지만, 3문 동시 발사에서는 원래 3문 단계의 추가 발열이 그대로 발생한다.

무장 정보

  • 그룹별 표에는 무기마다 각 동시 발사 수에서 생기는 추가 발열만 표시한다.
  • 그룹명은 IS MRM/SRM GROUP, IS ROTARY AC GROUP, IS LRM/THUNDERBOLD GROUP 등을 사용한다.
  • 공유 그룹이 없는 무기는 개별 그룹 - 개별 그룹으로 서로 영향 없음으로 표시한다.
  • 설명은 최고 추가 발열 적용 규칙과 AC/20 계열, AC/10 ×2 + Ultra AC/10 ×1 예시로 요약한다.

멕랩 표시

  • 현재 피팅의 유효 HSL을 반영한 뒤 고스트 힛 발생 조건을 만족하면 슬롯 영역 왼쪽 위에 경고 아이콘을 오버레이한다. 아이콘 표시 여부는 슬롯 위치를 바꾸지 않는다.
  • 발생 그룹에 참여하는 이동식·고정 무장 슬롯에는 빨간 외곽선을 표시한다.
  • 경고 아이콘 툴팁은 발생 그룹마다 한 줄씩 무기 구성 : 발열 88.8% (최종: 00.00, 고스트 힛: 00.00) 형식으로 표시하며 내용에 맞춰 폭을 정한다.
  • 발열 퍼센트는 쿼크 적용 후 무기 발열 합계와 고스트 힛을 더한 최종 발열이 현재 멕의 최대 발열 허용량에서 차지하는 비율이다. 현재 누적 발열은 포함하지 않는다.
  • 발열 퍼센트는 경고색 굵은 글씨, 고스트 힛 수치는 빨간색 굵은 글씨로 표시한다.
  • 발생 슬롯의 HEAT 툴팁은 최종 결과 모드에서 최종수치 + 고스트 힛, 쿼크 수치 모드에서 최종수치(쿼크수치) + 고스트 힛, 모든 수치 모드에서 최종수치(원본 ± 쿼크) + 고스트 힛 순서로 표시한다.
  • 멕랩의 ALPHA, HEAT, DPS 기본 수치에는 고스트 힛을 합산하지 않는다.

사격 시뮬레이션

정적 스펙만으로 놓치기 쉬운 사격 간격, 발열 누적, 냉각, 재밍과 거리 손실을 시간 흐름으로 확인하기 위해 현재 빌드의 무기를 브라우저 애니메이션 프레임에서 계산한다. 게임 전체를 복제하는 모드가 아니라 같은 조건에서 빌드 운용 경향을 비교하는 기획 도구다.

  • 사격 그룹 할당과 누름 상태를 관리하며 그룹별 시각 상태를 갱신한다.
  • 거리, 이동 상태, 맵 온도, 스플래시 적용, 과열 시 종료를 시나리오 조건으로 사용한다.
  • 일반 발사, 연속 피해, 번(burn), 연발 대기 탄환을 각각 처리한다.
  • 쿨다운·발열·사거리·ROF·무기 전용 쿼크와 타겟 컴퓨터 보너스를 적용한다.
  • 같은 시점에 발사된 무기를 고스트 힛 그룹별로 묶고 HSL로 보정된 발생 시점을 검사한 뒤 그룹에서 가장 높은 추가 발열을 시뮬레이션 열에 적용한다.
  • 고스트 힛 추가 발열은 JSON 원본 무기 발열과 쿼크 미적용 기본 사이클로 계산한다. HEAT·쿨다운·ROF 쿼크는 추가 발열 수치에 영향을 주지 않고 HSL만 발생 시점을 늦춘다.
  • 경과 시간, 총 피해, DPS, 발열은 무기 발사 컨트롤 바로 위에 함께 둔다.
  • 시뮬레이션 UI는 게임 배치에 가깝게 하되 시야와 즉시 판독성을 우선한다.

JSON 파서 법

데이터 갱신이 수작업 보정에 의존하지 않고 재현 가능하도록 게임 아카이브를 브라우저 JSON으로 만드는 추출 단계와 앱이 JSON을 읽어 계산 가능한 형태로 정규화하는 소비 단계를 함께 관리한다. 생성 JSON은 원본에 가까운 교환 데이터이며 화면별 파생 요약 저장소가 아니다.

브라우저 로딩과 결합

  • index.json에서 생성 파일 경로와 개수를 읽고 mechs.json, equipment.json, localization.json, loadouts.json, omnipods.json, skills.json을 로드한다.
  • 멕, 장비, 로드아웃, 옵니포드는 숫자 ID의 표현이 달라도 찾을 수 있도록 조회 경계에서 문자열 또는 정규화 키로 통일한다. 원본 ID 자체는 임의로 바꾸지 않는다.
  • 이름 매칭은 대소문자, 공백, 구분 기호 차이를 정규화한 검색 키를 사용한다. 표시 이름은 UI에만 사용하고 내부 이름·ID를 기본 결합 키로 둔다.
  • 장비 표시 이름 대치는 로드 직후 applyEquipmentDisplayNameOverrides()가 EQUIPMENT_DISPLAY_NAME_OVERRIDES의 소문자 item.name 키로 한 번만 적용한다. 원본 display_name은 source_display_name으로 보존하여 쿼크·시뮬레이션 이름 매칭 키에 계속 포함하고, 대치값은 UI 표시에만 쓴다. 생성 equipment.json은 재추출로 덮어쓰므로 대치 목록은 앱 코드에만 둔다. 현재 대치 대상은 NobleAutoCannon20을 NOBLE AC/20으로 표시하는 항목이다.
  • 누락 속성은 undefined, null, 빈 문자열을 구분해 처리한다. 의미가 확인되지 않은 누락값을 0, 빈 배열 또는 다른 레코드로 조용히 대체하지 않는다.
  • 숫자 필드는 계산 경계에서 유한 숫자로 변환하고, 퍼센트 multiplier의 부호 의미는 쿼크 종류별 규칙에 따라 해석한다.
  • 멕과 기본 로드아웃은 멕 ID로, 장비 장착 항목은 장비 ID로, 옵니포드는 현재 set과 component 또는 확정된 현재 ID로 결합한다.
  • 옵니멕의 유효 정의는 기본 차체를 복사한 뒤 현재 빌드의 부위별 옵니포드 하드포인트·내부 장비·고정 장비·쿼크를 합성한다. 원본 JSON 객체를 화면 상태 변경으로 직접 변형하지 않는다.

하드포인트와 장비 정규화

  • 하드포인트 타입은 대소문자를 제거해 energy, missile, ballistic, ams, ecm 등의 공용 키로 변환한다.
  • 하드포인트 ID는 선행 0을 제거해 비교한다. 예를 들어 "02"와 2는 같은 ID다.
  • 무기 수용량은 직접 WeaponSlot 자식 수를 추출한 weapon_slots를 사용한다. 매칭 자체가 없는 경우에만 1을 폴백한다.
  • 무기 계열은 가능한 경우 hardpoint_type 또는 stats.type으로 판정한다. 레이저·PPC·미사일·발리스틱 이름 목록을 코드에 반복해서 만들지 않는다.
  • 탄약 풀은 정규화한 활성 탄약 stats.type으로 결합한다. 선택형 아르테미스는 무기의 artemisAmmoType, 일반 상태는 ammoType을 쓴다.
  • 파생 검색 인덱스, 쿼크 요약, 하드포인트 배지와 통계 엔트리는 로드 후 브라우저 메모리에서 만들며 생성 JSON에 역으로 기록하지 않는다.

게임 데이터 추출

의도적인 게임 데이터 갱신은 반드시 tools/extract_mwo_data.py를 사용한다.

원본용도
Game/GameData.pak멕 목록, 장비, 로드아웃, 아르테미스 원본 속성, 스킬 노드와 배치

전체 추출

python tools/extract_mwo_data.py --game-dir "F:\Game\Steam\steamapps\common\MechWarrior Online" --out public\data

전체 추출은 localization.json과 skills.json을 포함한 모든 생성 JSON을 함께 갱신하며, 안전 갱신 게시 단계에서도 두 파일을 제외하지 않는다. localization.json은 English_xml.pak의 영문 키와 TRANSLATED TEXT를 원본 표기 그대로 보존하고 조회할 때만 선택적 선행 @와 대소문자를 무시한다. 멕 표시명은 내부 배리언트 키, 무기 표시명은 원본 Loc.nameTag의 번역 값을 사용하며, 이번 표시명 변경 대상이 아닌 설명·쿼크·비무기 장비명은 기존 ORIGINAL TEXT 기반 표시를 유지한다. 현지화 키가 존재하고 번역된 멕 이름이 정확히 (T) 접미사로 끝나는 멕은 실제 조립할 수 없는 항목으로 판정하여 멕과 기본 로드아웃 생성 데이터에서 함께 제외하되 원본 localization.json 키는 보존한다. MDF의 VariantType이 없거나 빈 일반형 멕은 현지화 이름 대신 원본 MDF Variant 코드를 최종 표시명으로 사용하고 이 필드가 없으면 추출을 중단한다. 비일반형의 현지화된 이름은 mech.chassis 키의 현지화된 카테고리명과 대소문자 구분 없이 일치하는 접두어 및 공백으로 시작하면 선행 카테고리명과 공백을 제거한다. 이름 전체가 카테고리명과 같거나 다음 문자가 공백이 아니면 유지한다. 카테고리가 정확히 두 단어 A CLAN이면 A CLAN, CLAN A, A 순서의 공백 경계 접두어도 제거한다. 내부 멕 키가 lgd로 끝나고 MDF의 VariantType이 Special인 멕은 정규화한 현지화 이름에 (LGD)를 한 번만 붙이며, MechID로 연결한 기본 로드아웃에도 같은 표시명을 저장한다. 기본 로드아웃은 원본 MechID로 정식 멕 배리언트 키에 결합하고 원본 Name은 source_name으로 보존한다. 키가 없으면 키 자체를 표시명으로 유지하고 갱신 보고의 별도 누락 목록에 기록한다. 게시 전 index.json의 현지화 문자열 수와 실제 키 수, skill_nodes와 일곱 카테고리의 실제 노드 합계를 대조한다.

하드포인트만 갱신

python tools/extract_mwo_data.py --game-dir "F:\Game\Steam\steamapps\common\MechWarrior Online" --out public\data --hardpoints-only

스킬만 갱신

python tools/extract_mwo_data.py --game-dir "F:\Game\Steam\steamapps\common\MechWarrior Online" --out public\data --skills-only

전체 추출은 설치된 게임의 모든 데이터를 다시 읽기 때문에 요청 범위 밖의 밸런스 값이나 숫자 형식도 바뀔 수 있다. 하드포인트 수정만 필요하면 --hardpoints-only로 기존 장비·로드아웃 데이터를 보존한다.

전체 추출은 모든 MDF의 Cockpit.ShakeDamping을 검사하고 값이 정확히 1.0인 멕을 shake_damping_mechs.json 하나에 모은다. 항목에는 멕 식별 정보, 원본 값, PAK와 MDF 경로를 보존하며, 속성이 누락된 멕이나 최상위 Mech.ShakeDamping 값은 이 목록에 포함하지 않는다.

스킬 노드 처리

  • Libs/MechPilotTalents/MechSkillTreeNodes.xml의 효과·적용 대상·요구조건과 MechSkillTreeNodesDisplay.xml의 노드 좌표를 결합해 skills.json을 생성한다.
  • 표시 좌표의 고정 열 범위로 FirePower, Survival, Mobility, JumpJets, Operations, Sensors, Auxiliary를 판정한다. 추출 시 원본 카테고리 순서와 정의/표시 노드 집합이 정확히 일치하지 않으면 오류로 중단한다.
  • 각 효과의 기본값과 Faction → WeightClass → Tonnage → Mech 중첩 조건을 원본 구조로 보존한다. Affects와 Require도 임의로 평탄화하거나 버리지 않는다.
  • --skills-only는 다른 생성 데이터는 유지한 채 skills.json과 index.json의 스킬 파일·노드 개수 메타데이터만 갱신한다.

NULL 옵니포드 처리

  • parse_mdf()는 각 MDF 컴포넌트의 명시적 OmniPod와 CanEquipECM을 멕 정의에 보존한다. 상세 옴니포드 XML의 컴포넌트 CanEquipECM도 해당 포드 레코드에 보존한다. 속성명은 대소문자를 무시해 읽고 생성 키는 CanEquipECM으로 정규화한다. parse_loadouts()는 원본 MechID로 같은 멕 MDF를 찾고 동일 컴포넌트 값을 기본 로드아웃 XML과 결합한다.
  • 빌드 가능한 로드아웃에 대응 MDF 정의가 없거나 MDF의 비후면 몸체 컴포넌트가 로드아웃에서 빠지면 추출을 중단한다. MDF 파싱 실패가 기존 로드아웃 값을 그대로 통과시키지 못하게 한다.
  • 로드아웃 XML 값이 없고 MDF 값이 있으면 MDF 값을 사용한다. 양쪽 값이 모두 있으면 같아야 하며, 다르면 이름이나 세트로 우선순위를 정하지 않고 추출을 중단한다.
  • 결합한 모든 ID는 OmniPods.xml에 존재하고 멕 chassis 및 component와 일치해야 한다. 하나 이상의 포드를 가진 옴니멕은 후면 장갑 컴포넌트를 제외한 모든 몸체 포드가 해결되어야 한다.
  • 로드아웃 CT의 원본 NULL은 이름 기반 추론 대상이 아니라 MDF와 결합하는 원본 구조다. MDF와 로드아웃 양쪽 모두 숫자가 없을 때에도 동일 이름, 접미사 제거, 컴포넌트 유사성만으로 포드를 자동 선택하지 않는다.
  • 현재 설치 데이터의 빌드 가능 옴니멕은 직접 원본 결합만으로 전부 해결된다. 과거 숫자·normal_body·shared_body override는 MDF 직접값으로 대체했고 별도 NULL 해소 파일을 제거했다. 양쪽 원본에 숫자가 없는 미래 예외는 자동 추론하지 않고 추출 오류로 보고한다.

전체 JSON 갱신 절차

  • 임시 출력에 전체 데이터를 추출한 뒤 JSON 구조, MDF 직접 옵니포드 결합 결과, 표준 멕과 옵니포드 하드포인트 회귀 기준을 검증하고 성공한 결과만 게시 데이터에 반영한다. 게시 파일은 기존 파일을 복구용 위치에 복사한 뒤 각 대상 위에 원자적으로 교체하며 중간 실패 시 전부 롤백한다. 기존 JSON 전체를 먼저 이동하지 않으므로 갱신 중에도 로컬 서버가 항상 이전 또는 새 파일을 읽을 수 있다.
  • 멕 아이콘 전체 갱신은 tools/extract_mwo_mech_icons.py로 수행한다. 스크립트는 GameData.pak의 Libs/UI/Screens/Assets/MechIcons/ 바로 아래 256×256 RGBA PNG를 추출해 basename을 소문자로 정규화하고, ReplaceIcon의 대소문자를 무시한 동일 파일명 교체본을 우선 적용한 뒤 local-mech-icons와 public/assets/mech-icons에 게시한다. 정규화된 파일명이 충돌하면 게시하지 않으며 대상 폴더에만 있는 별도 아이콘은 보존한다. PAK에 없는 현재 멕 아이콘은 기존 브라우저 폴더에 유효한 파일이 있는지 게시 전에 검사한다.
  • 갱신 보고에는 생성 JSON 범위, 멕·무기 현지화 누락 키 목록, MDF 명시 옵니포드 검증 수, 미해결 컴포넌트, 추가된 썸네일과 검증 결과를 포함한다. 차단 실패는 실패 단계와 게시 여부를 구조화해 보고하고, 게시 또는 staging 정리만 실패하면 이미 완료된 게시 상태와 정리 경고를 구분한다.
  • Windows 게시용 임시 파일은 최종 데이터 또는 썸네일 폴더 안에 만들고 교체 전후에 대상 폴더 ACL 상속을 활성화한다. transaction 및 backup 디렉터리도 사용자 상속 ACL을 적용해 사용자 소유 로컬 서버의 JSON 읽기와 실패 시 복구 파일 접근을 보장한다.
  • 미확정이나 해석 오류가 있으면 임시 결과를 게시하지 않는다. 모두 해결된 현재 전체 데이터는 조립 불가 (T) 멕을 제외한 멕 1,276개, 장비 751개, 영문 현지화 문자열 30,350개, 로드아웃 1,299개, 옵니포드 1,833개이며 현지화 누락 키, 미확정 옵니포드와 누락 썸네일은 모두 0건이다.
  • “전체 JSON 갱신”은 추출·검증·보고까지만 포함한다. 커밋, 푸시, GitHub Pages 배포는 별도의 명시적 요청이 있을 때만 수행한다.

추출 데이터 보존 원칙

  • 원본 속성은 덮어쓰지 않고 필요한 파생 필드를 추가한다.
  • 무기에는 ammoType, artemisAmmoType, alwaysHasArtemis를 보존한다.
  • 탄약에는 type, numShots를 보존한다.
  • 표준/아르테미스 무기와 탄약 대응 레코드가 실제로 존재하는지 검증한다. 누락 시 이름 치환으로 조용히 폴백하지 않는다.
  • 파생 요약과 캐시를 public/data/*.json에 영구 저장하지 않는다.

ETC

URL과 브라우저 히스토리

  • URL의 멕 식별자와 tab 쿼리를 선택 상태와 동기화한다. 뒤로·앞으로 이동 시 다섯 주 탭과 선택 멕을 함께 복원한다.
  • 신규 로드아웃 공유 URL은 loadout-url-codec.js가 원본 MWO 코드를 DEFLATE로 가역 압축하고 Base64URL로 변환한 z... 값을 loadout 쿼리에 담는다. URL 진입 시 압축 문자열 길이를 먼저 제한하고 압축 해제 결과도 최대 4,096바이트로 제한한 뒤 기존 importMwoCode 검증 경로에 전달한다. 과거의 전체 MWO 코드 loadout=A...도 그대로 읽으며, 유효하게 불러온 URL은 신규 압축 형식으로 교체한다. 압축과 복원은 브라우저 안에서만 수행하고 서버나 Firebase에 공유 코드를 저장하지 않는다.
  • fitting 쿼리는 공개 Firestore 문서 ID를 나타내고 일반 loadout·mech·tab 진입보다 우선한다. 공유 링크의 최초 적용은 현재 History 항목을 교체하고 브라우저 상세에서 적용하면 기존 탭의 빌드·공개 출처 스냅샷을 현재 항목에 보존한 뒤 새 항목을 추가한다. Back으로 이전 항목에 돌아오면 같은 탭에 스냅샷을 복원하며, 공개 핏팅 원상복귀는 현재 fitting URL을 유지한다. 일반 멕·주 탭·로드아웃 탐색 URL은 이전 fitting 쿼리를 제거한다.
  • 탭 전환만으로 유효한 현재 빌드나 비교 목록을 불필요하게 초기화하지 않는다.

현지화

  • 사용자 UI는 한국어와 영어를 지원한다. 게임 내부 이름, 장비 ID와 데이터 키는 번역 문자열을 계산 키로 사용하지 않는다.
  • 새 UI 문구는 가능한 경우 data-i18n 키와 번역 테이블을 함께 추가한다. 단위·약어·대시 표기는 같은 종류의 기존 화면을 따른다.

후원

  • 한국어에서 상단 후원하기를 누르면 카카오페이 QR 팝업을 연다. 우측 상단 X, 배경 클릭, Esc로 닫는다.
  • 영어에서는 팝업 대신 https://ko-fi.com/killkimno로 이동한다.
  • QR 이미지는 public/assets/kakaopay-donate-qr.png에 둔다.

도움말과 방문 통계

  • 원격 목록은 전체, 제목 옆 메뉴에서 선택한 한 mechId, 또는 추출 멕 데이터의 원본 chassis를 복제한 chassisKey 조건으로 조회한다. 멕 선택 메뉴의 기종 행은 확장 버튼과 선택 버튼을 분리해 +·-만 배리언트 목록을 열고 닫으며, 나머지 영역은 해당 기종 전체를 선택한다. 로컬 목록의 기종 필터는 저장 레코드를 마이그레이션하지 않고 로드아웃 분석 결과의 같은 키를 사용한다. 각 원격 쿼리는 표시용 100개와 다음 묶음 존재 확인용 1개까지 허용하며 실제 목록에는 앞의 100개만 합친다. 다음 묶음은 보관한 100번째 문서를 단일 커서로 이어 읽는다. 최신순·좋아요순 정렬은 브라우저 네이티브 셀렉트가 아니라 기존 핏팅 액션과 같은 공용 메뉴 트리거·화살표·팝오버 외형을 사용한다. 새 공개 문서는 mechId와 chassisKey를 포함한 스키마 v3로 저장하고, 기존 v1·v2 문서는 공유 읽기 호환을 유지한다. 게시·작성자 삭제와 좋아요 문서·집계 ±1은 보안 규칙으로 검증하며, 삭제와 좋아요 변경은 각각 트랜잭션으로 처리한다. 제목은 앞뒤 공백 없는 출력 가능한 ASCII 1~20자와 https 금지, 로드아웃 코드는 36~4096자와 MWO 섹션 형태만 허용한다.
  • 공유 URL은 현재 언어와 fitting={문서 ID}만 유지하고 로드아웃 코드를 싣지 않는다. URL 진입 시 Firebase와 앱 데이터 준비를 함께 기다리고 1~128자이며 슬래시가 없는 ID만 getDoc(fittings/{id})로 단건 조회한 뒤 기존 normalizeSnapshot과 공유 전용 openSharedFitting 경로로 적용한다. 공유 문서를 찾기 위해 공개 목록을 훑지 않으며 핏팅 문서 1회, 작성자 프로필 캐시 미스 시 users/{uid} 1회를 읽는다. 로그인 방문은 기존 좋아요 상태 동기화를 위해 사용자 좋아요 문서 1회를 추가로 읽는다. 문서 적용 완료 후 추천 표시 설정이 켜져 있으면 아래 추천 캐시·조회 경로를 별도로 실행한다. 누락·형식 오류·조회 실패는 상태 안내만 표시하고 앱 초기화를 유지한다. 문서 로딩 중 일반 멕·주 화면 탐색이 fitting 파라미터를 제거하면 취소 이벤트가 공유 요청 세대를 올려 늦은 응답이 현재 피팅을 덮지 못하게 한다.
  • fitting 문서 URL이나 브라우저의 공개·내 게시물 또는 추천에서 적용하면 해당 멕랩 탭에 원본 코드와 현재 앱에서 다시 인코딩한 기준 코드를 공유 출처로 저장하고 RIGHT ARM 아래에 제목·공유자·좋아요 여부 버튼·원상복귀 패널을 렌더한다. 브라우저의 applyFitting은 원격 문서를 openSharedFitting으로 전달하고 ensureLikeState로 사용자 좋아요 상태를 동기화한다. 추천의 applyRecommendation도 openSharedFitting으로 즉시 출처를 만들고 팝업을 닫은 뒤 hydrateRecordAuthors와 syncActiveSourceLikeState로 작성자·좋아요를 보충한다. 메타데이터 응답은 출처만 갱신하고 피팅을 다시 적용하지 않는다. 출처 패널에는 좋아요 수를 별도로 표시하지 않는다. 활성 공유 탭은 밝은 초록색, 비활성 공유 탭은 어두운 초록색으로 구분한다. 새 탭을 추가하거나 다른 탭으로 전환해도 기존 탭의 출처는 보존하고, 같은 탭을 다른 멕·일반 피팅으로 교체하거나 저장할 때 제거한다. 원상복귀는 현재 인코딩 코드가 기준 코드와 달라진 경우에만 활성화하며 원본 공개 코드를 다시 적용한다. 저장·인증 상태 안내는 3초 뒤 자동으로 숨긴다.
  • 데스크톱 멕랩의 실제 피팅 화면은 활성 피팅의 RIGHT ARM 아래에 같은 mechId를 가진 공개 핏팅을 likeCount 내림차순으로 최대 3개 표시한다. renderCommunityAreaPanel은 공유 출처 패널과 추천 패널을 순서대로 렌더하므로 공유 문서에서는 공유자·좋아요 버튼 아래에 추천 목록이 이어진다. 카드에는 제목·좋아요 수·기존 자동 태그와 적용 버튼을 표시한다. 버튼을 누르면 fittingDetailSectionsHtml을 통해 브라우저 상세와 동일한 장착 무기·상세 정보만 담은 간이 팝업이 열리며 X와 이 핏팅 적용만 제공한다. 개인설정의 추천 핏팅 보이기는 기본 ON이고 로컬 저장소에 보존한다. 다른 주 화면·멕 전체 목록·공유 문서 로딩 중에는 조회하지 않으며, 잘못되었거나 삭제된 공유 문서 조회가 끝나 실제 공유 피팅이 없으면 추천을 다시 허용한다.
  • 추천용 Firestore 쿼리는 mechId ASC + likeCount DESC 복합 인덱스와 limit(3)을 사용한다. 멕별 결과는 브라우저 로컬 날짜와 함께 mwolab:recommended-fittings:v1 로컬 저장소에 보존하고 진행 중 요청은 메모리에서 중복 제거한다. 같은 날짜에는 페이지를 다시 열어도 결과와 빈 결과를 재사용하고 날짜가 바뀐 뒤 해당 멕을 처음 볼 때만 다시 조회한다. 캐시가 없는 멕은 문서 최대 3개를 읽으며 빈 쿼리는 최소 1회 읽기로 과금될 수 있다. 추천 목록 조회·카드 표시에는 작성자와 사용자별 좋아요 상태가 없으므로 users와 likes 문서를 추가 조회하지 않고 실시간 리스너도 만들지 않는다. 실패 결과는 캐시하지 않는다. 공개 핏팅 게시·삭제·좋아요 변경 후에는 해당 멕의 메모리·로컬 캐시를 무효화하고 현재 멕이면 같은 최대 3개 쿼리를 다시 실행해 순위와 수량을 맞춘다.
  • admin/firestore.rules는 공개 목록 읽기, Google 로그인 게시·작성자 삭제·좋아요와 해당 사용자의 원자적 게시 카운터 변경만 허용하고 나머지는 기본 거부한다. 작성자 삭제 트랜잭션은 비공개 deletionRequests/{fittingId} 정리 요청을 함께 만들며, 로컬 관리자 목록 조회가 삭제된 부모 아래의 좋아요 문서를 제거한 뒤 요청을 지운다. 관리자 직접 삭제도 Admin SDK로 카운터를 함께 감소시키고 정리 요청을 남긴 뒤 좋아요 정리가 성공한 경우에만 요청을 제거하므로, 일시 실패하면 다음 목록 조회가 재시도한다. 카운터가 없거나 잘못되었으면 삭제를 거부한다. 기존 게시물이 있는 프로젝트는 관리자 작업을 중지하고 admin/firestore.maintenance.rules로 클라이언트 쓰기를 잠근 뒤 admin/sync-publisher-usage.mjs로 소유자별 카운터를 백필·재검증하고 운영 규칙을 배포한다. 규칙은 MWO 코드의 의미를 판정하지 못하므로 원격 핏팅은 열기 전에 기존 buildFromMwoCode 검증 경로를 통과한다.
